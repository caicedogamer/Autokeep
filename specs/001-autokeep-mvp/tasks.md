## Phase 5b: User Story 3 v2 — Flexible Import (Priority: P1)

**Goal**: an operator can import a CSV or JSON file of heterogeneous structure, see the inferred column-to-role mapping with confidence indicators, confirm or correct the mapping, then see a per-row validation report against the **normalized internal model** before any record is written, and choose to commit only the valid rows or cancel entirely. Parser-level failures touch zero records (FR-015, SC-004, SC-020).

**Independent Test**: import (a) a file with canonical column names and order — mapping auto-confirms with no operator interaction; (b) a heterogeneous file with es/en column names in non-canonical order — preview shows inferred mapping + confidence, operator confirms; (c) a file with an ambiguous column pair (e.g., `Importe` and `Saldo` both numeric) — preview flags `AMBIGUOUS_ROLE` and operator picks; (d) a file missing a required role — confirm is blocked; (e) an unparseable file — parser-level rejection touches zero records. Verify in every case the records list and `ImportBatch.mappingDecision` reflect exactly the operator-confirmed mapping.

## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: no dependencies — can start immediately
- **Foundational (Phase 2)**: depends on Setup completion — **BLOCKS** all user stories and the workspace UI phase
- **User Stories (Phases 3–8)**: all depend on Foundational; can then proceed in parallel (or sequentially in priority order P1 → P2 → P3)
- **Workspace UI (Phase 9)**: depends on Foundational; should be picked up early in parallel with US1 because the app cannot be operated by a real user without it
- **Polish (Phase 10)**: depends on the user stories it covers (the WCAG sweep and the no-plaintext-at-rest audit need every primary route to exist, so they land last)

### User Story Dependencies

- **US1 (P1, records CRUD)**: depends only on Phase 2; no story dependencies
- **US2 (P1, filters)**: depends only on Phase 2; subscribes to records via the records module's public surface but does not require records UI to exist before its own services + tests are runnable (uses an in-memory record fixture)
- **US3 (P1, import)**: depends only on Phase 2; commits records via `RecordsService` from US1 — schedule import work to start when US1 services land (T036), even if US1 UI is in flight
- **US4 (P2, export)**: depends on US1 (records exist) AND US2 (filter state is the export scope); start after US2 services land
- **US5 (P2, dashboard)**: depends on US1 (records) AND US2 (filter state); start in parallel with US4 once US2 services are ready
- **US6 (P3, AI)**: depends on US1 (records to learn from); can start in parallel with US4/US5

### Within Each User Story

- Tests for a story (where included) MUST be written and FAIL before the implementation they cover
- Domain types + Zod schemas before services
- Services before UI
